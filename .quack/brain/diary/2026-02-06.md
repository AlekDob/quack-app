## Welcome Screen Flash Fix

**Problema**: Durante l'avvio, l'utente vedeva un flash della welcome screen ("What will you build today?") tra lo splash screen e l'UI completa caricata. Esperienza scattosa e non professionale.

**Root cause**: Due bootstrap paralleli in race condition:
- Bootstrap agenti (veloce, ~50ms) chiamava `setBooting(false)` per primo
- Bootstrap principale (lento, ~200-500ms) caricava progetti/terminali dopo
- Risultato: UI sbloccata prima che i dati fossero pronti → condizione `terminals.length === 0 && persistedProjects.size === 0` era `true` → welcome screen visibile

**Soluzione**:
- Rimosso `setBooting(false)` e `setHasBootstrapped(true)` dal bootstrap agenti
- Solo il bootstrap principale (che finisce dopo aver caricato tutto) controlla `booting`
- Gli agenti si caricano in parallelo ma non influenzano il gate della UI

**File modificati**:
1. `src/App.tsx` — 7 righe rimosse dal bootstrap agenti (riga ~5654-5661)
2. `index.html` — fade-out splash da 0.5s → 0.8s (più morbido)
3. `src/App.tsx` — timeout DOM removal da 500ms → 800ms

**Risultato**:
```
Prima:  splash → welcome screen (flash 100-400ms) → UI completa
Ora:    splash → UI completa (transizione fluida)
```

### Insight

**Gate keeper pattern**: quando hai multiple async operations in parallelo, identifica quale dovrebbe essere il gate keeper che sblocca la UI. Nel nostro caso, il bootstrap principale che carica `terminals` e `persistedProjects` è l'unico a dover controllare `booting`.

## Session History Cross-Contamination Fix

**Problema critico**: Quando l'utente aveva due sessioni (A e B) dello stesso agente e switchava velocemente, Claude rispondeva nella sessione B con contesto della sessione A. L'utente diceva "sì procedi" in B e riceveva risposte su argomenti di A.

### Root Cause

`chatConversationHistoryRef` era una `Map<agentId, history[]>` invece di `Map<sessionId, history[]>`:
- Tutte le sessioni dello stesso agente condividevano lo stesso storico
- Quando mandavi messaggio in B, il prompt includeva lo storico di A
- Claude rispondeva nel contesto sbagliato

### Soluzione (Fase 1)

Cambiato chiave del ref da `agentId` a `sessionId` in 3 punti:
- `sendMessageForAgent` (righe 2218, 2328): usa `messageKey` (= `activeSessionId`)
- `clearCurrentAgentConversation` (riga 3440): usa `activeSessionId || activeId`

**Effetto**: ogni sessione ha ora il suo storico isolato, zero bleed tra sessioni dello stesso agente.

### Problemi Secondari Trovati

L'analisi ha rivelato altri 5 bug di architettura mista Agent-First/Session-First:
1. `abortStreamForAgent` legge `activeSessionId` al momento della chiamata invece che capture-time
2. RepositoryGroup usa `chatSessions.get(agent.id)` (chiave sbagliata)
3. Multi-listener result handler usa `chatSessions.get(agentId)` (chiave sbagliata)
4. Rust fallback `agent_id` quando manca `session_key`
5. Race condition nella lazy hydration con switch rapido

**Fase 2 e 3** pianificate ma non ancora implementate (fix secondari + hardening).

### Brain Entries Created

- `bugs/bug-session-history-cross-contamination.md` — root cause analysis, soluzione, problemi secondari, pattern estratto

## Security: .env Cleanup and Giphy Fix

Analisi di sicurezza sulle variabili d'ambiente embedded nel DMG/build:

### Problema

Variabili nel `.env` che non dovrebbero essere lì:
1. **Lemon Squeezy API key** (JWT 1.2KB) — leftover da migrazione a Gumroad, mai usato nel codice
2. **Apple app-specific password** in plaintext — rischio se `.env` viene esposto
3. **Giphy env var naming mismatch** — `.env` definiva `VITE_GIPHY_API_KEY`, codice cercava `VITE_giphyApiKey` → feature non funzionante

### Cosa finisce effettivamente nel build

**Safe (client-side by design)**:
- Supabase URL + anon key (protette da RLS policies)
- PostHog analytics key
- Gumroad product ID (pubblico)
- Giphy API key (free tier)

**NON finisce** (correttamente escluso):
- Lemon Squeezy key (non referenziato)
- Apple credentials (solo per xcrun durante build)

### Soluzione

**Cleanup completato**:
1. Rimosso `LEMON_SQUEEZY_API_KEY` e `LEMON_SQUEEZY_STORE_ID` dal `.env`
2. Fixato `giphyService.ts:9` — `VITE_giphyApiKey` → `VITE_GIPHY_API_KEY`
3. Aggiunto warning + istruzioni per spostare Apple password nel Keychain:
   ```bash
   xcrun notarytool store-credentials "quack-notarize" \
     --apple-id "..." --team-id "..." --password "..."
   ```

**File modificati**: `.env`, `giphyService.ts`

### Insight: Build-Time Secrets Separation

Server-side secrets (Apple password, API keys inutilizzati) dovrebbero vivere separati dalle build-time env vars che vanno inline nel JS bundle. Il `.env` attuale mescola le due categorie — va bene perché `.gitignore` protegge il file, ma il Keychain sarebbe più sicuro per Apple credentials.

## Agent Teams: SDK Analysis e GrowthBook Gate

Investigato perché il `TeammateTool` non appare nella lista tool disponibili nonostante il toggle sia attivo.

### Root Cause: Server-Side Feature Flag

L'SDK ha **due gate** per registrare il `TeammateTool`:

1. **Env var `AGENT_TEAMS=1`** → PASS (propagata correttamente da Rust → Node → SDK)
2. **GrowthBook feature flag `tengu_amber_flint`** → FAIL (A/B test server-side di Anthropic)

Il flag `tengu_amber_flint` viene scaricato dal server di Anthropic all'avvio dell'SDK. Se non è `true` per l'account corrente, il default è `false` → `TeammateTool` non viene registrato.

### Situazione attuale

| Gate | Status | Note |
|------|--------|------|
| Env var | PASS | Setup completo e funzionante |
| GrowthBook flag | FAIL | Rollout graduale, fuori dal nostro controllo |
| tmux installato | FAIL | Richiesto per TmuxBackend (multi-pane teammates) |

### Implicazione

Il nostro **setup è production-ready** (roster, CLAUDE.md, UI, toggle), ma il **runtime peer-to-peer** è bloccato lato Anthropic. Possiamo continuare con l'approccio attuale (Team Lead usa Task/subagent) finché il flag non viene attivato per tutti gli account.

**Prossimo step**: `brew install tmux` (prerequisito), poi aspettare che Anthropic abiliti il flag per l'account.

## Visual Feedback: Team Badge + TeammateWidget in Chat Stream

Implementato feedback visivo per Agent Teams direttamente nel chat stream.

### Componenti creati

1. **TeamModeBadge** (`StreamMessage.tsx`) — badge compatto con mini avatar di ogni membro + nome team, visibile su ogni messaggio assistant quando un team è attivo
2. **TeamMemberMiniAvatar** (`StreamMessage.tsx`) — avatar 16x16 con overlap (-4px) per effetto "stack" nel badge
3. **TeammateWidget** (`TeammateWidget.tsx`) — widget inline che appare quando il Task tool spawna un teammate, mostra avatar + nome + ruolo + stato (pulse/spinner per attivo, dot grigio per completato)

### Task → Teammate Matching

Quando il chat stream renderizza un `Task` tool use, il nome del task viene confrontato con i nomi dei membri del team attivo. Se c'è match, viene renderizzato un `TeammateWidget` invece del widget generico.

### Avatar Fix: useAgentInfo → useAgentAvatar

**Bug**: tutti i mini avatar nel badge e nel TeammateWidget mostravano il duckdroid default.

**Root cause**: `useAgentInfo` è progettato per droids (`.claude/agents/` YAML), normalizza l'ID a kebab-case e matcha contro `list_agents`. Gli agenti unificati hanno UUID come ID → nessun match → fallback duckdroid.

**Fix**: sostituito con `useAgentAvatar` hook + frontend enrichment pattern:
- `TeamMember` in `types.ts` ha ora `avatar?` e `color?` opzionali
- `teamStore.ts` accetta `agentAvatars: Map` e arricchisce i membri dopo il ritorno da Rust
- `RepositoryGroup.tsx` costruisce la mappa avatar da `TerminalInfo[]` e la passa a ogni `loadActiveTeam`
- `TeamCreationModal.tsx` costruisce la mappa e la passa a `createTeam`

**Principio**: Rust gestisce persistenza, Frontend gestisce presentazione. Avatar/color sono dati puramente visuali.

### File modificati

| File | Modifica |
|------|----------|
| `types.ts` | `avatar?`, `color?` in TeamMember |
| `teamStore.ts` | `agentAvatars` param in createTeam e loadActiveTeam |
| `TeamCreationModal.tsx` | Costruisce e passa avatar map |
| `RepositoryGroup.tsx` | `buildAgentAvatarMap` helper, aggiornate 3 chiamate |
| `StreamMessage.tsx` | useAgentAvatar, TeamModeBadge, TeamMemberMiniAvatar rewrite |
