## Web build heap cap

**Purpose:** Cap the Node heap for the `apps/web` build and its Vitest workers so a React Compiler memory blowup on `ChatView.tsx` OOMs the process instead of the whole machine.
**Stack:** Node (via `NODE_OPTIONS`), Vite build, Vitest worker `execArgv`.

### Files

| Type   | Path                                                   | Purpose                                                                                 |
| ------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| Config | `apps/web/package.json` (`build` script)               | Sets `NODE_OPTIONS=--max-old-space-size=8192` before `vite build`.                      |
| Config | `apps/web/vite.config.ts` (`test.execArgv`)            | Sets `--max-old-space-size=8192` for Vitest workers.                                    |
| Test   | `apps/web/src/components/chatHotPath.compiler.test.ts` | `HOT_PATH_MODULES` line budgets — the actual long-term containment, not the memory cap. |

### Root cause

`babel-plugin-react-compiler` runs against `ChatView.tsx` (~12k lines). Its per-component dataflow analysis grows super-linearly with file size, not linearly. Under `bun` (JavaScriptCore, no default heap ceiling) this ran past 12 GB and triggered a macOS watchdog reboot — observed 2026-08-06 and again 2026-08-12. Under `node`, the same unbounded growth is an ordinary OOM crash of the process, not the OS.

### Fix

Run the build and Vitest workers under `node` with an explicit heap cap (`--max-old-space-size=8192`), so the failure mode is contained to the process.

- `NODE_OPTIONS` chosen over hardcoding a `node_modules/.bin/vite` path: that shim is a symlink generated by bun, and its shape on Windows isn't guaranteed. `NODE_OPTIONS` is read by whatever node process the shim ultimately launches, regardless of the shim's form.
- Vitest 4 removed `poolOptions`, so the cap lives at the top-level `test.execArgv`, not nested under a pool config.

### Measurements (2026-08-12)

| Module         | State                            | RSS     | transformSync duration |
| -------------- | -------------------------------- | ------- | ---------------------- |
| `ChatView.tsx` | pre-fix (compiler bails out)     | 0.32 GB | 535 ms                 |
| `ChatView.tsx` | post-fix (no bailout, full walk) | 4.24 GB | 33.2 s                 |
| `Sidebar.tsx`  | —                                | 0.70 GB | —                      |

8 GB was picked (not 4 GB) because the post-fix single-file peak is already 4.24 GB.

### Follow-up (open)

`ChatView.tsx` is 11,978 lines against a budget of 11,737 in `HOT_PATH_MODULES` (`chatHotPath.compiler.test.ts`) — the ratchet is currently red. Raising the memory cap is a safety net, not the fix: the real long-term mitigation is splitting `ChatView.tsx`, not raising the heap ceiling further.
