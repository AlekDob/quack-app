- [00:00] (Alek) Workspace color fix + custom picker. Prod couldn't color new projects while dev could + old projects kept their color → not a logic bug (id/color-key are deterministic from the normalized root, symmetric set/read), but a full prod `localStorage`: existing color keys survive, new `setItem` fails. Root cause was masked because `setJson` swallows quota errors silently. Fix: `setWorkspaceColor` now surfaces a toast when the write fails. KEY INSIGHT: "old keeps / new fails, dev ok / prod no" is the signature of a full per-origin localStorage, not a code path difference.

- [09:03] (Alek) **New chats now default to Milo (not Jack)** in the composer pill. Default was already wired (`DEFAULT_PRESET_ID = "builder"` + `applyDefaultPreset()` on every new-chat path), but the pill kept showing Jack: `presetId` state seeded to `null` (= Jack) and the corrective `applyDefaultPreset()` runs inside `paintSession`'s `startTransition` (deferred, low-priority) so the initial frame stuck on Jack. Fix = seed `useState(DEFAULT_PRESET_ID)` in `AIChatPanel`; restored sessions still overwrite via the found-branch (`found.presetId ?? null`), so legacy chats correctly keep Jack. Also confirmed perf: switching permMode (Plan/Auto/Bypass) is a `useState` + in-memory `Map` write in `permModeStore` (zero I/O, no CC re-spawn), and preset/agent management is a light re-render reading from an in-memory override cache — neither touches the heavy mount surfaces gated by `memo(WorkspaceShell)` + `useWorkspaceHeavyMount` (058). KEY INSIGHT: a value applied only inside `startTransition` won't win the first paint against the initial `useState` — seed the state with the intended default instead of relying on a deferred effect to correct it.
- [08:50] (Alek) **Cold project-switch loader** (`079`, sibling of `075`). Some projects still feel laggy on switch-in; rather than chase every ms, mask the cold mount with a branded full-window wash in the project's color. `workspaceSwitchLoader.ts` (begin on cold switch = `prevId && !isWorkspaceWarm(id)`, end on editors-ready; SHOW_DELAY 90 / MIN_VISIBLE 320 / CAP 2500) + `WorkspaceSwitchVeil.tsx` (radial gradient in `--ws-load-color` over `--bg`, initials badge + name, pulse). Warm (last-3) projects skip it → still instant. Also added `switchPerf.ts` — dev-only `[switch-perf]` timing (`markSwitchStart` + `logSwitchPhase` on FileTree root list_dir + editors-ready) because the existing `[chat-switch]` logs only measure `setActiveWorkspace` (fast) and miss the real mount cascade. KEY INSIGHT: the switch-slowness criterion is warm-vs-cold, not project size — instrument the uninstrumented phases, and where you can't cheaply cut the cost, mask it (perceived perf) with the per-project color the design system already reserves for identity.
- [09:05] (Alek) **New-chat intermittent slowness — unmemoized host fan-out.** Investigated the create-chat path: `addNewAIChat` → `pulseChatSwitch({veil:false})` (no flush), `addAIChat` (persistWs is debounced, not sync), `focusAIChat` (light). So the cost is the render cascade: adding a chat mutates `loaded` → `WorkspaceShell` re-renders and re-creates EVERY mounted `AIChatHost`, and since `AIChatHost` wasn't memoized each re-rendered its full 7382-line `AIChatPanel`. So new-chat cost scaled O(#mounted panels) — intermittent because it depends on how many chats you have open/sticky. Fix: `memo(AIChatHost)` (props are primitives + stable container/root refs) so only the new host + the one losing focus re-render — mirrors `memo(WorkspaceShell)`. Also added dev `[new-chat-perf]` timing (`markNewChat` in addNewAIChat + `logNewChatPhase` panel mounted/painted in AIChatPanel) to confirm click→mount cost. KEY INSIGHT: same root cause as the project-switch fanout — big unmemoized components re-rendering N-wide on an unrelated `loaded` mutation; memoize the per-item host so one item's change doesn't re-render the rest.
- [09:15] (Alek) **Chat-switch intermittent stall — diagnosis.** Same-workspace chat switch doesn't flush (flush only cross-ws) and has the veil, so the cost is on the target: the transcript render is NOT windowed — `turns.map(groupChatTurns(display))` (AIChatPanel ~6167) renders EVERY turn. Messages apply via `startTransition` (JS non-blocking) but the layout/paint of hundreds of turns (each with markdown + tool renders + UserTurnBar) blocks the main thread → "incaglia". Intermittent = depends on the target chat's transcript length. Feature 076 already flagged message virtualization as the follow-up. Added dev timing `[chat-switch] transcript painted { count, elapsedMs }` (rAF×2 after messages applied in `applyLoadedMessages`) to correlate turn count with paint cost. Decision (Alek): commit the diagnosis now, then implement turn-windowing WITH regression tests (nav-rail `021` per-turn anchors + jump-to-turn must handle hidden turns → expand-on-jump). NEXT.
