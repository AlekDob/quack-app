# 2026-08-06

- (Alek) Tracked down the "conversations freeze, can't send a second message" regression to `54bd78d92` (cherry-pick of upstream `6c4153c59`). Key insight: the server started emitting `provider.approval.respond.failed` **without** a `responseCommandId` when settling stale approvals on `session.started`, and only the server projection knew that shape — the web reducer bailed out, kept the approval `pending`, and `ChatView`'s queued-composer dispatch stayed blocked on `activePendingApproval` until the next full snapshot. That snapshot is why the freeze "healed itself after many minutes" instead of looking like a hard bug.
- Fix: `apps/web/src/storeEventReducer.ts` now mirrors `ProjectionPipeline.ts` (stale detail + no response command → `uncertain`), idempotent across repeated session starts. Regression test added in `storeEventReducer.test.ts` (52 passing).
- Bug record: `documentation/bugs/2026-08-06-composer-queue-stuck-stale-approval.md`
- (Alek) Fixed tool rows rendering **above** the avatar/name line in Claude threads. The avatar isn't a fixed part of the turn: it rides on the first row that declares `showPaperoAvatar`, and standalone `work` rows never declared it. So when tools ran before any assistant text, the identity landed on the Thinking row below them. Now a leading work group wears the turn's avatar (`MessagesTimeline.logic.ts` + render slot in `MessagesTimeline.tsx`), gated on the turn actually having a user message so a bare "Context compacted" row stays avatar-less. Also hoisted the flag when `collapseSettledTurns` folds such a row away. Test: `MessagesTimeline.logic.test.ts`.
- (Alek) Il Mac si è riavviato tre volte: un `babel.transformSync` con React Compiler su `ChatView.tsx` (12.192 righe) è arrivato a 12,3 GB in 11 secondi e il watchdog del SoC ha forzato il reboot. Non era uno script inventato — è la copia esatta di `compileEvents()` in `chatHotPath.compiler.test.ts`, che gira a ogni `bun run test`. Insight vero: la memoria del React Compiler cresce **più che linearmente** con la dimensione del file, e lo script incriminato girava sotto **bun** (JavaScriptCore, nessun tetto di heap di default). Node si auto-limita a ~4288 MB su questa macchina e muore da solo; bun no, e si porta giù il sistema. I worker di vitest girano già sotto node, quindi la suite non era il pericolo — lo era il debug a mano.
- Paracadute messo (Parte A): `maxLines` per modulo in `HOT_PATH_MODULES` + una suite `chat hot-path size ratchet` che conta le righe (veloce, non aspetta il compile da minuti). I budget sono le dimensioni di oggi: possono solo scendere. Più una regola in `CLAUDE.md`: mai compilare un modulo hot-path sotto bun.
- Scoperto durante la verifica: il test del compiler su `ChatView.tsx` è **rosso anche a HEAD** (`Handle TryStatement without a catch clause`, riga 8485). Le modifiche non committate lo risolvono (try/finally → `Promise.finally`) ma ne introducono un altro: `paperoIdForSendRef.current = activePaperoId` scritto in render (riga 1230). L'helper `readPaperoIdForSend` che dovrebbe sostituirlo esiste già ma non è chiamato da nessuno — migrazione a metà, 5 call site ancora sul ref.
- Standing rule extracted: **every settlement rule in the server `ProjectionPipeline` must be mirrored in the web `storeEventReducer`** — the two are independent projections of the same activity stream, and a divergence fails silently (wrong UI until the next snapshot) rather than loudly.
