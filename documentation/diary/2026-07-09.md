- [Fix] (Alek) Agent Hub no longer flashes a purple "needs-input" dot + quack sound at session start when the agent is actually still working. Root cause: `AskUserQuestion` can't render under `-p`, so the overlay auto-redirects it (deny "ask in plain text") within ms — but `AgentHubWatcher.onRequest` fired `needs-input` for questions IMMEDIATELY (no grace, unlike permissions), and `onSettled` never cleared a settled question (only on focus), so the poll's `waiting` guard pinned it purple for up to `NEEDS_INPUT_TTL` (90s). Fix: questions now go through the SAME `PERM_GRACE_MS` (600ms) timer as permissions, and `onSettled` cancels that timer for both kinds — a redirect that settles before the grace never flashes anything. `AgentHubWatcher.tsx` `onRequest`/`onSettled`. See feature 009-agent-hub.
- [Fix] (Alek) A recovered Claude Code / Cursor session could render the entire flattened first-turn prompt (`[System] You are Jack…`) as one giant user bubble that covered the whole chat (title became `[System]`). Root cause: on turn one `flattenMessages` packs `[System]\n…\n\n[User]\n<text>` into the single `-p` prompt; the CLI stores that whole packet as its first user message on disk, and `chatProviderRecovery.recoverSessionFromProvider` re-imports it verbatim when the Quack row is thinner. The existing sanitizer only dropped `role:"system"` rows, not `role:"user"` ones carrying the scaffold. Fix: new `stripCliFlattenScaffold` in `chatTextUtils.ts` unwraps the `[System]…[User]…` packet to keep only the real user text (cuts later `[Assistant]`/`[Tool result]` sections); wired into `cleanStaleToolMessages`'s user-message map, so it heals already-corrupted sessions on next load AND every future recovery. See feature 044-provider-session-bridge.
- [Fix] (Alek) Context & Usage drawer no longer flashes the amber "Plan limits: request failed: http status: 429" box at session start. The claude.ai `claude_usage_limits` OAuth endpoint rate-limits aggressively (429) and the 30s poll fires immediately on chat open; the first transient failure was surfaced as an error even with THIS CHAT at 0. Now the poll catch treats 429/rate-limit/network blips as non-errors, keeps the last-known cached limits silently, and only shows an error when there is genuinely no data AND the failure isn't transient. `AIChatPanel.tsx` poll catch (~L3481). See feature 019-usage-monitor.
- [Fix] (Alek) Opening a project AFTER boot showed its AI chats as EMPTY (and typing into one could overwrite the real on-disk transcript). Root cause: chat transcripts render from a per-workspace in-memory cache (`chatStoreCache.ts`) hydrated via `hydrateChatStore(wsId)`, but that was called in only ONE place — `store.hydrate()` at boot, and only for the workspaces open at boot (`survivingIds`). `openWorkspace` (used by the picker, ActivityBar, Command Palette, Agent Mode, `actions.ts`) loaded `state.json` (so the chat TABS appeared) but never hydrated the chat cache → `loadSessions(wsId)` returned `[]` → empty panes; a subsequent `saveSession` then `chat_store_save`-overwrote that session's disk file with the partial new transcript (other sessions survive because the Rust save re-reads+merges `__idx__.json`). Fix: `openWorkspace` now `await hydrateChatStore(meta.id)` before the `set(...)` that mounts the panels (idempotent — no-op when already warm). Switching between already-open projects was unaffected (panels unmount on `isActive` toggle → flush; cache stayed warm from boot). `store.ts` `openWorkspace`. See feature 043-chat-transcript-persistence.
