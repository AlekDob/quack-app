# Companion (astronaut) typecheck cascade closed, chat hot path recompiles

## Astronaut/Companion: from ~180 typecheck errors to 0

The imported Companion provider was added to `ProviderKind` without being added to
anything that is exhaustive over it. Two root causes explained nearly every error:

1. `astronaut` was missing from every per-provider `Record<ProviderKind, …>` map and
   from every exhaustive `switch`.
2. `AstronautModelSelection` was the only `ModelSelection` member without an
   `options` field, so `modelSelection?.options` stopped typechecking everywhere.

Fixing the two causes centrally collapsed roughly 50 errors in two edits:

- `packages/contracts/src/model.ts`: added an empty `AstronautModelOptions` schema and
  wired it into `ProviderModelOptions`; `ProviderWithDefaultModel` now excludes both
  `pi` and `astronaut`.
- `packages/contracts/src/orchestration.ts`: `AstronautModelSelection` reuses that schema.
- `packages/shared/src/model.ts`: `hasDefaultModel()` became the single predicate for
  "this provider discovers its catalogue at runtime", plus a new
  `providerWithDefaultModel()` helper for the call sites that need a concrete fallback.
  Every `provider === "pi"` check in web and server now routes through those two.

Opportunistic DRY along the way: `ProfileSettingsPanel` dropped a hardcoded 20-line
provider-label switch in favour of `PROVIDER_DISPLAY_NAMES`, `projectDefaultProvider`
uses the same map for its "no available models" message, and the `serverSettings`
test fixture now spreads the defaults so a future provider cannot break it.

## React Compiler: ChatView compiles clean again

The imported features had silently knocked `ChatView.tsx` out of React Compiler
(a bailout means the whole component loses auto-memoization). Two triggers, both
listed in `chatHotPath.compiler.test.ts` and both fixed at the root:

- a `throw` inside a `try` in `onSavePaperoInstructions` — the try/catch moved to
  `savePaperoInstructionsFailure()` in `ChatView.logic.ts`, which returns a message
  instead of throwing;
- the Claude auth recovery callback: a value block read inside a `catch` closure, and
  a manual dependency list naming `activeThread?.worktreePath` where the compiler
  inferred `activeThread`. Both hoisted to consts above the callback.

## Companion: sezione impostazioni dedicata + test connessione

L'URL del Companion stava dentro "Installed CLIs", accanto alle versioni delle CLI, con
anche un box "CLI docs" vuoto. Companion è un servizio HTTP, non una CLI. Ora ha una voce
propria nelle impostazioni (gruppo Coding, dopo "Agent providers"): `CompanionSettingsPanel.tsx`,
sezione `companion` in `settingsNavigation.ts` e nell'indice di ricerca.

Il pulsante "Test connection" non ha richiesto niente di nuovo lato server: l'RPC
`provider.listModels` accetta già `apiEndpoint` e per astronaut fa `GET {url}/models`.
Un successo prova insieme raggiungibilità e risposta reale, quindi il test è una
`useMutation` sopra quell'RPC, cronometrata con `performance.now()`. Zero schema,
handler o health check aggiuntivi.

Verificato a runtime su istanza isolata (porte 3899/5899): il Companion reale ha
risposto "Connected · 8 models · 856 ms", e la riga Companion non compare più tra le
Installed CLIs.

## `make mac-app` appeso: syspolicyd incastrato, e un bug nascosto dietro

Alek: "si blocca e non fa nulla". Il log si fermava dopo `Building mac/dmg` e restava lì.

Tre cause distinte, una dietro l'altra.

**1. L'output è nascosto.** `commandOutputOptions` manda `stdout` a `"ignore"` quando non
sei in verbose (`scripts/build-desktop-artifact.ts:356`). Electron-builder compila i moduli
nativi in silenzio per minuti, quindi "fermo" e "sta lavorando" si vedono uguali.
`SYNARA_DESKTOP_VERBOSE=1 make mac-app` per vedere.

**2. `syspolicyd` incastrato — la causa vera del blocco.** Il demone macOS che valida le
firme del codice era a 970 MB (secondo processo più pesante della macchina, uptime 6 giorni,
2.2 GB di swap). `sample` sul Python di gyp fermo: 2645 campioni su 2645 dentro
`dlopen → mapSegments(CodeSignatureInFile) → fcntl`, bloccato. 0% CPU.

Lo stesso guasto si presentava in tre forme diverse, e questo ha portato fuori strada:

- `library load denied by system policy` su `_ctypes` (il file era sano: firma valida, e
  gli stessi comandi passavano a freddo);
- il build appeso per sempre dentro `dlopen`;
- binari nativi (`oxfmt`, `oxlint`, `tsgo`) uccisi con SIGKILL appena partiti.

Cura: `sudo killall syspolicyd`. Si riavvia da solo — dopo, 140 MB e tutto passa. Se torna,
riavviare il Mac. Non era il codice: "l'altro ieri andava" perché la macchina era sana.

**3. `assertPackagedMacDeviceHelper` esplodeva su `dist/*.dmg`.** Visibile solo dopo aver
risolto il punto 2, perché prima non ci si arrivava mai. La funzione cicla su tutto il
contenuto di `dist`, file inclusi, e costruisce
`dist/Quack-2.0.0-arm64.dmg/Quack.app/Contents/...`. Il `.dmg` è un file: `fs.exists` non
risponde `false`, tira `ENOTDIR`. Ora salta le voci che non sono directory.

Build verificato end-to-end: DMG + zip + `latest-mac.yml` in `release/`. fmt, lint (0 errori),
typecheck 7/7.

Aperto e non fatto: estendere `resolvePythonForNodeGyp` (riga ~1126, oggi solo Windows) a
macOS puntando a `/usr/bin/python3`. Il python di Homebrew è firmato adhoc, ed è proprio
quel tipo di firma che syspolicyd fatica a validare sotto carico.

- [16:40] (Alek) **Kernel panic durante `make mac-app`: il build web sotto bun senza tetto di heap.**
  Il panic (`watchdog timeout: no checkins from watchdogd in 93 seconds`, 16:07) è la stessa
  firma del 2026-08-06. Causa: `make mac-app` -> `bun run dist:desktop:dmg:arm64` ->
  `bun run build:desktop` -> turbo (packageManager `bun`) -> `vite build`, quindi il preset
  React Compiler girava sotto JavaScriptCore, che non ha un limite di heap di default.
  Perché proprio ora: il pull ha portato `1e32e731d`, che ha eliminato i tre bailout di
  ChatView. Finché bailava, il compiler si fermava subito. Misurato con `transformSync` +
  `babel-plugin-react-compiler` su un solo file, sotto node:
  ChatView pre-pull 535 ms / 0.32 GB RSS -> post-pull 33.2 s / 4.24 GB RSS (Sidebar 0.70 GB).
  Il cap a 4 GB in `vite.config.ts` copriva solo i worker di vitest, niente copriva il build.
  Fix: `apps/web/package.json` build ora è
  `NODE_OPTIONS=--max-old-space-size=8192 vite build` — non un path hardcoded a
  `node_modules/.bin/vite`, perché quel file è un symlink generato da bun e la sua forma
  su Windows non è garantita (il repo supporta Windows: shim `.cmd`, dev-runner in shell
  mode). `NODE_OPTIONS` è letto dal processo node che lo shim di vite lancia comunque,
  quindi non dipende da come lo shim è fatto. `test.execArgv` sale a 8192 perché 4 GB ora
  è sotto il picco reale. Build verificato via `bun run build`: 55 s, picco 6.56 GB RSS,
  DMG a posto.
  Aperto: `ChatView.tsx` è a 11 978 righe contro il budget 11 737 di `HOT_PATH_MODULES`, quindi
  il ratchet `chat hot-path size` è rosso. È esattamente il segnale che il file va spezzato —
  la memoria del compiler cresce più che linearmente con la dimensione.
